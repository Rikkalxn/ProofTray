## SnapBridge 的处理依据

公开的 Nikon 帮助将相机存储卡的缩略图浏览、全屏查看和下载尺寸区分开；支持的 RAW 可以下载机内约 2MP JPEG 副本。
这不能单凭帮助页证明所有网格图都是 2MP，也不能证明 Z6 II 在所有连接模式下都能返回同样大小的图。

已有本地 SnapBridge 2.13.3 分析中，缩略图仓库有独立的大图读取路径，发送 `GetLargeThumb (0x90C4)` 和对象句柄。
该动作的能力判断没有用 DeviceInfo 的操作列表挡住请求。独立的 `GetLssImage (0x9522)` 则区分 VGA（参数 1）
与 FULL_HD（参数 3），并检查能力支持。只记录互操作事实，没有复制官方实现、资源或库。

这些路径直接接收相机提供的压缩图片，不需要手机先下载完整 NEF 并解拜耳。
机身内部究竟复用已存的嵌入图、缓存图，还是按请求生成缩小副本，现有证据不足以逐机型确定。
把百来像素的缩略图插值放大不能增加用于选片的真实细节。

## 本项目发现与修复

此前的预览读取存在三个问题：

1. 扩展命令必须出现在 DeviceInfo 中才调用，与上述 Nikon 大缩略图路径存在差异。
2. 第一个成功返回的数据就被采用，没有根据真实解码尺寸决定是否继续找更大图。
3. 只要缓存文件存在就停止请求；`detail` 文件名还会优先于更清晰的 `grid` 文件，低清回退可能被长期保留。

现在的顺序和目标：

| 场景 | 读取顺序 | 停止升级的目标 |
| --- | --- | --- |
| 可见网格 | 大缩略图 → 机内 VGA 副本 → FHD 副本 → 标准小缩略图 | 长边 ≥640、短边 ≥360 |
| 单张 / 比较 | 大缩略图 → FHD 副本 → 机内 Full HD 副本 → 标准小缩略图 | 长边 ≥1600、短边 ≥900 |

目标用于选择读取策略，不是机型输出保证，不会强制上采样来“达标”。已得到有效图片时不再请求标准小缩略图。
若所有可用通道都达不到目标，保留像素最多的有效结果；较小的新结果不会覆盖已有较大缓存。
部分模式返回 HEIF 时，先用系统解码器检查尺寸，不能解码则继续尝试其他已知读取通道。

只有 Nikon 的大缩略图命令允许能力表缺项时探测；机内 VGA/Full HD 与 FHD 命令仍需能力报告。
明确不支持的操作在本次连接中停用，缺少某张照片的预览不会被误判为整台相机永久不支持。
设备忙、会话错误和无效对象句柄不会当作“需要换一个预览格式”继续发送命令。

网格仍只请求可见项，离屏尚未开始的请求可取消。会话内记录最近 4096 个“照片 + 质量档”的已完成尝试，
避免无法提升的照片在滚动时不断重取；重连会允许再次尝试。底层 PTP 事务仍串行，不在传输事务中间插队。
预览只写应用缓存/RAW 预览归档，不加入图库、系统相册或“已导入”记录，不触发整张卡的原片下载。

预览记录增加可选 `previewRevision`，缓存内容升级但文件名不变时也会通知 Compose 重新解码；旧目录没有该字段仍可读取。
RAW 预览归档和本地原片 URI 保持分离。很小的显示结果标为“小缩略图”，没有把模糊图描述为高清。

## 下次真机检查

- 使用包含本次改动的新构建，连接 Z6 II 后重开原先模糊的照片；不需要先删除旧缓存或原片。
- 分别观察网格和单张查看的加载、原始比例、方向与清晰度，再断开相机检查缓存。
- 日志标签 `OpenBridgePreview` 记录场景、操作码、是否声明支持、返回码、字节数和真实解码尺寸；不记录照片内容或文件名。
- 用 `adb logcat -s OpenBridgePreview OpenBridgeCamera` 查看是否先后取到了大图，还是因当前连接模式/照片格式回退。
- 只有确认正确调用仍无大图时，再评估从 NEF 的内嵌 JPEG 按需分段读取；本轮未加入完整 RAW 下载或渲染作为自动兜底。

新增 `CameraPreviewPolicyTest` 用例覆盖能力缺项、厂商边界、明确拒绝、VGA/Full HD 参数、小图继续升级、较大缓存优先及错误分类；
2026-10-31 按用户打包安装请求执行，7 个用例全部通过。
