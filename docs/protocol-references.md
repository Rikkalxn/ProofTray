# 协议参考与验证边界

本轮按用户最新授权对其手机上的 SnapBridge 2.13.3 做了本地反编译核对。
APK 与分析产物位于 `private/`，不随仓库提交。JADX 1.5.6 的完整处理有 33 个还原错误，不能把所有反编译输出视为可靠源码。
未执行官方 APK 中的原生库，也未把其源码、库或资源放进 OpenBridge。

PTP/IP 请求构造与数据集解析为本项目代码；以公开 PTP/IP 格式及 libgphoto2 协议定义交叉检查。
蓝牙配对哈希和 Blowfish 使用 MIT 授权的 furble 参考实现，许可证随源码和 APK 保留。

## 已核对的字段

- BLE 主服务：`0000de00-3dd4-4255-8d62-6dc7b9bd5561`。
- 配对、客户端名称、连接配置、连接建立分别为同一基址下的 `2000`、`2002`、`2004`、`2005`。
- Wi-Fi 建立请求使用 `2005` 的 bit 0。连接配置中的 SSID / 密码是加密字段，不按明文读取。
- PTP/IP 命令与事件是两条 TCP 连接；无主机发送数据的操作使用 `DataOut = 1`，包括相机到手机的数据。
- 标准分段读取 `0x101B` 参数为对象句柄、32 位偏移、最大字节数。
- 尼康 `0x9431` 扩展为句柄、偏移低 / 高 32 位、长度低 / 高 32 位，必须检查设备能力。
- 主机登记预备 / 确认为 `0x952B` / `0x935A`；确认参数 `0x2001`。应用不会通过等待固定时长自动确认配对码。
- 大预览 `0x90C4 GetLargeThumb`、`0x920F GetFhdPicture` 均传对象句柄；标准小缩略图为 `0x100A`。
  2026-10-30 核对本地 SnapBridge 的大缩略图路径后，Nikon 的 `0x90C4` 允许在能力表未列出时作一次兼容读取探测；
  明确返回 OperationNotSupported 后，本会话不再向其发送该操作。其他厂商仍按能力表限制。
  增加已报告能力的 `0x9522(handle, 1/3, 0)` 机内 VGA / Full HD 副本作为后备；按实际像素尺寸选择结果，不以操作成功当作高清。
  这些是已拍照片读取，不涉及实时取景或读取完整原片；具体机型输出尺寸仍需实测。细节见 [预览质量说明](preview-quality.md)。

## 后台与位置通道核对

以下来自本地 SnapBridge 2.13.3 的接口 / 数据结构检查，以及公开 N-link 行为对照；只记录互操作事实，未复制官方实现或库。

- BLE `2008` 是请求位图：低 4 位校时、接下来 4 位位置、再接下来 4 位连接请求；它不是认证成功确认。
  配对状态依据 `2000` 四阶段结果，避免等待一个并非所有机型都会发出的校时请求。
- 2026-10-31 继续核对 BLE Java 调用链与 native 密钥生成：第四阶段的 nonce 字段不用于回显校验。
  会话密钥由第四阶段相机 DeviceID、客户端 DeviceID，以及第二/第一阶段 nonce 的前四字节组合，经同一 CBC-MAC 派生。
  本项目保留第二阶段密码学证明和阶段/长度校验，补齐密钥生成；不再套用其他参考实现的第四阶段 nonce 比较。
  应用身份握手与系统经典蓝牙配对是两个步骤，不能因握手通过就报告整个配对流程完成。
- BLE `2005` bit 1 请求经典蓝牙，bit 0 请求 Wi-Fi；bit 7 为不再需要数据连接，须看 `2009` 能力位。
- 小图路径使用经典蓝牙 SPP UUID `00001101-0000-1000-8000-00805f9b34fb`，有手机主动连接 / 相机连接手机两种方向。
  身份帧标识 `0xA1A1` / `0xA2A2`，数据帧 `0xA5A5`，数据内部为 PTP 容器。数据通道单独验证挑战，不复用未经验证的旧会话。
- `0x9520` 参数 `0x11` / `0x22` 控制自动传输开始 / 结束；`0x9521(0)` 读取机内待传列表。
  观察到的列表布局为固定 48 字节头、每项 8 字节、8 字节尾，条目包含对象句柄、估算大小和图像类型。
- `0x9522(handle, 3, 0)` 对应 FULL_HD / MPF_CLASS2；获取的是机内便携图像，不等价于 RAW 原件。
  Wi-Fi 手动小图也可在能力支持时使用 `0x920F`；不支持就报错，不拿 `0x100A` 的小缩略图代替。
- GPS 为 41 字节，BLE `2007` 或 PTP 数据出 `0x9523`。经纬度编码是度、分、分的小数两组百分位，不能把后两字节误当成秒。
  UTC、有效性位图、可选海拔 / 卫星数、16 字节 WGS-84 名称分别编码。无效位置通过有效标志清除，不伪造 0,0 坐标。
- N-link 当前 `scheduleAutoSync()` 按句柄倒序筛掉已传输项并限制数量；这与严格“本次连接后新增”不同。
  OpenBridge 的 Wi-Fi 原图自动下载采用会话基线、存储修订和文件身份去重；蓝牙小图消费机身待传列表。

核对的本地类包括 `ConnectBluetoothAction`、`GetAutoTransferListAction`、`GetLssImageAction`、`BleLocationInformationData`。
这些路径尚未完成真实机身协议抓包验证，尤其是不同机型的 RFCOMM 方向、能力报告和暂停后恢复行为。

## 2026-10-31 Z6 II 自动传图实测

本地 SnapBridge 2.13.3 与 N-link `042b5214de661819a5c257adda81f0863498706f` 用于行为对照。
N-link 的自动同步主要运行在已建立的 Wi-Fi / USB 会话上，不把它当作经典蓝牙自动传图已经实现的证据。

- 扫描广播中的相机名称可能以零字节填充，按第一个零字节截断，再进行完整名称匹配；否则扫描列表能看到相机而重连找不到它。
- `2009` 的 bit 13 表示 BTC cooperation；该能力要求手机监听 SPP，由相机连接手机。
  保留两种手动方向覆盖，默认按能力选择。手机主动连接分支兼容 RFCOMM channel 1；系统限制该接口时使用公开 SPP API。
- 传图前读取 `2008`，只清除连接请求位，保留校时和定位请求；再写入 `2005 = 0x02`。
- Z6 II 在进入数据通道前释放 BLE。此型号兼容分支按已识别的型号应用，没有把同样行为强加给整个 Z 系列。
  数据连接完成独立身份验证后读取 DeviceInfo、打开 PTP 会话，再开始自动传输并读取待传列表。
- 已在 Z6 II / 小米 Android 16 上收到 3 张 1620×1080 JPEG，手机媒体库分别记录完整文件尺寸，队列状态为完成。
  这是机内便携副本，不是 JPEG 原图或 RAW。随后再次读取待传列表为空，未重复下载。
- 传完关闭数据 socket，再恢复 BLE；机身首次连接返回状态 19 时重新扫描并限重试一次。
  旧传输的 `0x80` 释放请求不得发送给恢复后的新 GATT 会话，否则会立即使待机连接再次断开。
- 开启便携 JPEG 自动下载后，手动连接、配对完成和重新连接都会立即检查一次，此后等待通知。
  手动检查可主动恢复控制连接；错误结果保留在设置页，Wi-Fi 断开或连接失败时释放应用内的优先占用。
- 最终候选包实测：先检查空列表并恢复 BLE；随后用户新拍 1 张，`2008` 通知触发第二批传输，未点击手机检查按钮。
  新照片保存后再次恢复 BLE，状态为已认证、系统已配对。已验证首次检查、后续通知与回到待机的完整循环。
- 相机也会主动结束空闲 GATT 会话；自动下载开启时，以低功耗扫描等待所选相机的待传广播。
  匹配服务 UUID、完整相机名称和厂商数据中的 AutoTransfer 位；仅有待传标记才尝试重连，仍须系统配对和应用身份验证。
  用户主动断开停止自动重连；连续连接失败停止尝试并保留手动重试入口。重新打开应用时从前台恢复传输服务。
  真机复测：保持 BLE 未连接，新拍 RAW 后由广播触发连接，自动保存对应的 1620×1080 JPEG，再恢复 BLE 待机。

以上区分参考行为、已实现行为和本机实测。长时间后台运行、其他机型、持续拍摄和功耗仍需分别记录。
